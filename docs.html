Quickstart

On a fresh Debian/Ubuntu VPS (root or sudo):

curl -fsSL https://install.vpscontrol.wazestudio.com | sudo bash

The script installs Docker, Go and Nginx automatically if needed, builds the panel, creates the working directories, and installs a systemd service that starts VPS Control automatically (including after a server reboot). It then asks you two questions, covered below: which domain (or none) to use, and whether to also enable a daily safety-net update check on top of the instant GitHub webhook described further down.

On your first visit to the panel, a setup screen asks you to create the first admin account — an identity that belongs to VPS Control, separate from your SSH/root access.

Prefer cloning the repository yourself instead of the one-liner?

git clone https://github.com/Wazestudio/vps-control.git
cd vps-control
sudo bash scripts/install.sh

Both methods run the exact same installer — the one above just downloads it for you first.

Domain or IP, HTTPS

During installation, you'll be asked:

Domain name already pointing at this VPS (leave empty to use the server's IP directly):

You have a domain name — enter it. The installer configures Nginx and then runs Certbot to obtain a Let's Encrypt certificate. Certbot will ask its own usual questions (contact email, accepting the terms) exactly as if you had run it by hand.

Remember to point an A DNS record at the VPS's IP before running the installer (or right after — you can always rerun Certbot later with sudo certbot --nginx -d yourdomain.com).

You don't have a domain — leave it empty and press Enter. The installer then asks for a port (8443 by default), generates a self-signed certificate, and configures Nginx to serve the panel over HTTPS directly on the VPS's IP:

https://YOUR_IP:8443
With a self-signed certificate, the browser shows a security warning the first time — that's expected, click "advanced" then "proceed". You can always switch to a real domain later by rerunning the installer.

Custom domains & SSL per app

Each deployed app has its own Domains tab. Point any hostname at one of the app's ports and VPS Control does the rest, directly on the host — no SSH needed:

  • Generates the Nginx reverse-proxy config for that domain and enables it (nginx -t then a reload — nothing is applied if the config is invalid)
  • Optionally requests a free Let's Encrypt certificate via Certbot for that domain, right when you add it (or later, from the same tab)
  • Shows the certificate status (HTTP only / active / error) and lets you retry a failed request once your DNS is in place
  • Removing a domain deletes its Nginx config and certificate and reloads Nginx
Point the domain's A record at the VPS's IP before requesting a certificate — Certbot has to reach the server over HTTP to validate ownership. If it fails (DNS not propagated yet), the domain still works over plain HTTP and you can retry SSL from the same tab once the DNS is ready.

A domain can only be pointed at a port already allocated to that app (its default port or one of its extra allocations) — not at an arbitrary port on the server.

Updates

VPS Control isn't a site you drop somewhere — it installs and runs like a system service, the same way nginx or docker do: a binary, a systemd unit, and well-known file paths (see the layout table below). "Update" means: pull the new code, rebuild the binary, restart the service — exactly like updating any other service. Three ways to trigger that:

  • Instantly, on every push (GitHub webhook) — the panel's System tab shows a payload URL and a secret; add them as a webhook on the repo (Settings → Webhooks → Add webhook, content type application/json, event "Just the push event") and every push to GitHub is applied to the running service within seconds.
  • From the panel — a button in the System tab triggers git pull + rebuild + service restart on demand, no SSH needed.
  • A daily safety-net check — if enabled at install time, a systemd timer (vpscontrol-update.timer) checks once a day and updates on its own in case a webhook push was ever missed. Optional, off by default, since the webhook is the primary path.

In every case, the service only restarts if the rebuild succeeds — if something goes wrong, the panel keeps running on the previous version.

File layout

Same idea as installing nginx: fixed, predictable paths rather than files scattered wherever a deploy tool happens to drop them.

WhatWhere
Binary/usr/local/bin/vpscontrol
Source (used for updates)/opt/vpscontrol-src
Data (accounts, DB connections, deployments, secrets)/opt/vpscontrol/data
Deployed applications/opt/vpscontrol/apps
systemd unit/etc/systemd/system/vpscontrol.service
Nginx site config/etc/nginx/sites-available/vpscontrol.conf
TLSLet's Encrypt via Certbot (domain), or self-signed at /etc/vpscontrol/ssl/ (IP)

Features

  • Admin accounts that belong to the panel, separate from SSH/root, multiple accounts (admin / read-only)
  • Full web-based file manager (browse, edit, upload, download, delete)
  • Docker service management (start/stop/restart/remove, logs)
  • Deployment from a public GitHub repo or a .zip file, with automatic stack detection
  • Custom domains per app, reverse-proxied through Nginx, with one-click Let's Encrypt SSL (Certbot) — all from the web
  • Quick MySQL or PostgreSQL database creation in a container
  • Database browser (tables, rows, free-form SQL queries)
  • One-click updates from the panel, or instantly via a GitHub webhook on every push

Architecture

The panel is a single Go binary: the frontend (vanilla HTML/CSS/JS) is embedded into it via go:embed, so there's nothing to build on the Node side. Accounts, database connections and deployments are stored in a simple local JSON file — no database to run for the panel itself. Every deployed application runs in its own Docker container, which isolates apps from each other and lets the panel drive their lifecycle (start/stop/restart) through the Docker CLI. Nginx acts as the reverse proxy and terminates TLS (Let's Encrypt via Certbot, or a self-signed certificate for direct IP access) — both for the panel itself and for any custom domain you point at a deployed app.

Known limitations

  • One container per application — no automatic multi-container orchestration (no generated docker-compose)
  • Database connection passwords are stored in plain text in the local JSON file (permissions restricted to root, but not encrypted)
  • No live build logs yet during a deployment
  • The service runs as root to drive Docker and browse the system's files
  • No fine-grained roles per deployment (a "read-only" account sees everything, no per-project scoping)

Roadmap

  • Streaming build logs (Server-Sent Events) during docker build
  • Encryption at rest for database connection passwords
  • docker-compose templates for multi-container stacks (app + DB + cache)
  • GitHub webhooks to redeploy your own deployed apps automatically on every push (the panel itself already supports this for its own updates)
  • Deployment history with rollback
  • Per-container CPU/RAM stats on the dashboard
