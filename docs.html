Quickstart

On a fresh Debian/Ubuntu VPS (root or sudo):

curl -fsSL https://install.vpscontrol.wazestudio.com | sudo bash

The script installs Docker, Go and Nginx automatically if needed, builds the panel, creates the working directories, and installs a systemd service that starts VPS Control automatically (including after a server reboot). It then asks you two questions, covered below: which domain (or none) to use, and whether to also enable a daily safety-net update check on top of the instant GitHub webhook described further down.

On your first visit to the panel, a setup screen asks you to create the first admin account — an identity that belongs to VPS Control, separate from your SSH/root access.

Prefer cloning the repository yourself instead of the one-liner?

git clone https://github.com/Wazestudio/vps-control.git
cd vps-control
sudo bash scripts/install.sh

Both methods run the exact same installer — the one above just downloads it for you first.

Domain or IP, HTTPS

During installation, you'll be asked:

Domain name already pointing at this VPS (leave empty to use the server's IP directly):

You have a domain name — enter it. The installer configures Nginx and then runs Certbot to obtain a Let's Encrypt certificate. Certbot will ask its own usual questions (contact email, accepting the terms) exactly as if you had run it by hand.

Remember to point an A DNS record at the VPS's IP before running the installer (or right after — you can always rerun Certbot later with sudo certbot --nginx -d yourdomain.com).

You don't have a domain — leave it empty and press Enter. The installer then asks for a port (8443 by default), generates a self-signed certificate, and configures Nginx to serve the panel over HTTPS directly on the VPS's IP:

https://YOUR_IP:8443
With a self-signed certificate, the browser shows a security warning the first time — that's expected, click "advanced" then "proceed". You can always switch to a real domain later by rerunning the installer.

Users & isolation

VPS Control has its own accounts, completely separate from your SSH or root access. Two roles are available:

  • Admin — can manage other panel accounts, create servers, and access global system pages (all Docker containers, all databases, activity log, system info). Admins do not automatically see other users' apps.
  • Read-only (viewer) — sees only the dashboard, the "My apps" list, the Deploy page, and their own API tokens.

Strict isolation — this is the core design rule:

  • Every user (including admins) only sees the apps they own, plus the ones where they've been invited as a collaborator.
  • An admin cannot open, edit, or even view another user's app unless that user has sent them a collaboration link.
  • The dashboard's service / app counters are filtered per user — no accidental leak of "who owns what" through counts.
This is a deliberate change from many panels where "admin" means "access to everything". If you're used to that model, the first login may surprise you — you'll see your apps, not everyone's.

Inviting a collaborator to an app — from the app's page, in the Collaborators tab. You pick permissions (console, files read, files write, settings, backup) and generate a link. The invited user accepts the link once, and from then on sees only that specific app.

Servers & quotas

VPS Control uses a Pterodactyl-style layered model: instead of every user deploying apps directly to the VPS, each app belongs to a server, and each server belongs to a user.

  • Only admins create servers (from the Servers page in the admin sidebar).
  • Each server has a name, an owner, and optional quotas: disk (MB), max number of apps, RAM (MB, informational), CPU quota (% informational).
  • One user can own multiple servers — for instance "Prod" and "Staging".
  • When deploying an app, the user picks one of their servers. Quotas are checked at that moment: if the server's app limit is reached, or its disk quota is exceeded, the deployment is refused.

Which quotas are really enforced?

QuotaEnforced?
Disk (MB)Yes — deployment refused if the server is over quota
Max appsYes — deployment refused when the limit is hit
RAM (MB)No — informational only (the RAM is shared at the VPS level)
CPU quota (%)No — informational only
A user with no server assigned cannot deploy anything. The Deploy page shows a clear "Contact an admin" message instead of the deployment forms.

Deleting a server — you choose what happens to its apps:

  • Delete them — containers, folders, backups and Nginx vhosts are removed. Irreversible.
  • Move them — you pick another server (same owner) and all apps are moved there first, then the empty server is deleted.

The confirmation modal shows exactly what will be removed (number of apps, servers, backups, domains, disk used) before you click the red button.

GitHub integration

To deploy private repos or organization repos, connect your GitHub account using a Personal Access Token (PAT) — no OAuth app to create, no callback URL, works immediately.

Step 1 — create the token (on github.com):

  • Go to github.com/settings/tokens/new
  • Give it a name like VPS Control
  • Check the repo scope (full control of private repositories)
  • If you need organisation repos, also check read:org
  • Click Generate token and copy it — GitHub shows it only once

Step 2 — connect it in the panel: go to API Tokens → GitHub and paste the token.

Step 3 — deploy: on the Deploy page, switch to My GitHub repos. You'll see the full list of repos your token can access, including private ones (marked with a 🔒) and organization repos. Pick one, give it a name, pick a target server, and deploy.

Security: the token is stored locally in the panel's JSON file (permissions 0600, root-only, same as the DB connection passwords). It is never returned by the API once saved, and it is not written into .git/config after the clone — the remote URL is reset to the clean HTTPS URL once the repository has been fetched.

Cascade deletion

When an admin deletes a user from the Users page, a confirmation modal first shows a preview of everything that will be removed: number of servers, apps, backups, domains, and total disk used.

Confirming removes all of it, cleanly:

  • Docker containers stopped and removed
  • Docker images tagged vpscontrol-<app> removed
  • Backup archives (.tar.gz) deleted from disk
  • Nginx vhosts and symlinks removed
  • Let's Encrypt certificates deleted (via Certbot)
  • App folders deleted from /opt/vpscontrol/apps/
  • GitHub token, API tokens, subuser entries, invitations cleaned up
  • Servers owned by the user removed last
Admins cannot delete their own account, and cannot delete the last remaining admin. This prevents a panel lockout.

Deleting a single app (from its Settings tab → Danger zone) uses the same cascade logic, scoped to that app.

Custom domains & SSL per app

Each deployed app has its own Domains tab. Point any hostname at one of the app's ports and VPS Control does the rest, directly on the host — no SSH needed:

  • Generates the Nginx reverse-proxy config for that domain and enables it (nginx -t then a reload — nothing is applied if the config is invalid)
  • Optionally requests a free Let's Encrypt certificate via Certbot for that domain, right when you add it (or later, from the same tab)
  • Shows the certificate status (HTTP only / active / error) and lets you retry a failed request once your DNS is in place
  • Removing a domain deletes its Nginx config and certificate and reloads Nginx
Point the domain's A record at the VPS's IP before requesting a certificate — Certbot has to reach the server over HTTP to validate ownership. If it fails (DNS not propagated yet), the domain still works over plain HTTP and you can retry SSL from the same tab once the DNS is ready.

A domain can only be pointed at a port already allocated to that app (its default port or one of its extra allocations) — not at an arbitrary port on the server.

Updates

VPS Control isn't a site you drop somewhere — it installs and runs like a system service, the same way nginx or docker do: a binary, a systemd unit, and well-known file paths (see the layout table below). "Update" means: pull the new code, rebuild the binary, restart the service — exactly like updating any other service. Three ways to trigger that:

  • Instantly, on every push (GitHub webhook) — the panel's System tab shows a payload URL and a secret; add them as a webhook on the repo (Settings → Webhooks → Add webhook, content type application/json, event "Just the push event") and every push to GitHub is applied to the running service within seconds.
  • From the panel — a button in the System tab triggers git pull + rebuild + service restart on demand, no SSH needed.
  • A daily safety-net check — if enabled at install time, a systemd timer (vpscontrol-update.timer) checks once a day and updates on its own in case a webhook push was ever missed. Optional, off by default, since the webhook is the primary path.

In every case, the service only restarts if the rebuild succeeds — if something goes wrong, the panel keeps running on the previous version.

Features

  • Multi-user with strict isolation — every user only sees their own apps, even panel admins
  • Per-user servers with quotas (disk, max apps) — Pterodactyl-style, enforced on deploy
  • Admin / read-only roles, panel accounts separate from SSH/root
  • GitHub integration via Personal Access Token — deploy public and private repos, plus organization repos
  • Full web-based file manager (browse, edit, upload, download, delete)
  • Docker service management (start/stop/restart/remove, logs)
  • Deployment from a public GitHub repo, a private one, or a .zip file, with automatic stack detection
  • Automatic subfolder detection for apps that live inside a folder in the repo
  • Custom domains per app, reverse-proxied through Nginx, with one-click Let's Encrypt SSL (Certbot)
  • Quick MySQL or PostgreSQL database creation in a container
  • Database browser (tables, rows, free-form SQL queries)
  • Cascade deletion for users and servers — containers, images, folders, backups, vhosts, certificates
  • One-click updates from the panel, or instantly via a GitHub webhook on every push
  • Upload limit: 30 MB per ZIP (configurable in Nginx)

Architecture

The panel is a single Go binary: the frontend (vanilla HTML/CSS/JS) is embedded into it via go:embed, so there's nothing to build on the Node side. Accounts, servers, database connections and deployments are stored in a simple local JSON file — no database to run for the panel itself. Every deployed application runs in its own Docker container, which isolates apps from each other and lets the panel drive their lifecycle (start/stop/restart) through the Docker CLI. Nginx acts as the reverse proxy and terminates TLS (Let's Encrypt via Certbot, or a self-signed certificate for direct IP access) — both for the panel itself and for any custom domain you point at a deployed app.

The isolation model is enforced at the middleware level: every request to an app's API endpoints first checks that the caller either owns the app or has been invited as a collaborator. Admins bypass this check only for global pages (Docker, users, servers, activity), never for another user's app.

Known limitations

  • One container per application — no automatic multi-container orchestration (no generated docker-compose)
  • Database connection passwords and GitHub tokens are stored in plain text in the local JSON file (permissions restricted to root, but not encrypted at rest)
  • RAM and CPU quotas on servers are informational only — real enforcement still happens at the container level via per-app limits
  • No live build logs yet during a deployment
  • The service runs as root to drive Docker and browse the system's files
  • No fine-grained roles within an app for the owner — the granularity is between users (owner / collaborator), not inside a single user's account

Roadmap

  • Streaming build logs (Server-Sent Events) during docker build
  • Encryption at rest for database connection passwords and GitHub tokens
  • docker-compose templates for multi-container stacks (app + DB + cache)
  • Push from the panel to GitHub (commit edits made in the built-in editor)
  • Deployment history with rollback
  • Per-container CPU/RAM stats on the dashboard
